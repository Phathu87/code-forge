# Release gate validation protocol

Requirements 257–301 are the acceptance contract. All checks below are pending unless backed by reviewed evidence for the exact release artifact. A screen, timer, fixture or passing build is never production evidence.

## Evidence and decision process

Catalogue: release/gates.json. Assessment: release/assessment.json. Run `npm run release:check -- web` (or pwa/android/ios/huawei/windows/verified/employer). Missing, failed, incomplete or mismatched evidence returns exit code 1. This local command is not connected to a deployment pipeline and cannot prevent an operator bypassing it; integrate it before publication. Human reviewers must open and verify evidence references: the validator checks record structure, not authenticity or test correctness.

For each passing gate record status=PASS, reviewer, testedAt (ISO timestamp), evidence (nonempty restricted report references), commit, environment and artifactSha256. Top-level identity must match the artifact, and engineering/security/operations/product sign-offs must be named. Never insert secrets or private test accounts into this public JSON. A new artifact invalidates prior evidence. Record failures and unknowns in the report; never turn unknown into PASS or silently waive critical/high blockers. Run the new-account journey against the intended production environment before approval; staging evidence alone cannot assert a production test passed.

## Core QA (258–278, 281)

- 258: Inventory every core navigation link and action: landing, registration/auth/verification/recovery, onboarding/profile, JS/React path/content, catalogue/detail/Shared Preferences, editor/persistence/execution/preview/tests/Coach, progress/XP/achievements, projects/portfolio/evidence, notifications, settings/privacy/support/export/deletion. No hidden mocks, dead actions or placeholders.
- 259: Fresh account → verify → login → onboard → select JS/React → learn → Shared Preferences → edit → autosave → run → preview → tests → deliberately fail/recover → permitted hint → correct/pass → server progress/XP/evidence → create/complete/publish eligible project → public portfolio → logout/login → persisted progress. No manual data edits or developer rescue. Record artifact and test-account references securely.
- 260–261: For profile/path/progress/workspace/source/project/achievements/portfolio, compare source hashes and remote revisions before/after refresh, logout/login, network loss, backend restart, app update, mobile suspend/resume and desktop restart. During editing, disconnect, kill, refresh, suspend, fail saves and time out APIs. Verify local drafts, non-corrupt remote state, resumed sync, conflicts and comprehensible status. Any substantial reproducible source loss is critical.
- 262: Signup/login/logout/verification/reset/refresh, expired/invalid sessions, deletion auth and sensitive reauthentication. Repeated attempts, malformed/expired reset and verification tokens, manipulated user IDs must fail safely.
- 263: Use learner A/B, reviewer/admin and anonymous accounts against every endpoint directly. Deny cross-user workspace/source/attempt/project/profile/integrity reads and writes; deny learners hidden tests/reviewer notes/admin access; constrain reviewers; expose only explicitly public resources. UI routing is not backend authorization.
- 264: Isolated hostile test environment only. Exercise infinite loop, memory/fork abuse, traversal, internal/metadata egress and background processes. Prove process/filesystem/tenant isolation, CPU/memory/time/process/output limits, dependency allowlist, denied networks and cleanup. Any credible production escape is critical.
- 265: Attempt token, parent DOM, internal API, desktop bridge and other-workspace access from learner preview. Verify actual origin and sandbox boundaries plus independent API authorization.
- 266: Visible pass/fail, timeout, runtime errors, malformed output and infrastructure failure. Service failure must not become learner failure, lost XP or misconduct evidence; retries must be safe.
- 267: Send manipulated XP/completion/achievement/evidence/project fields and duplicate/replayed concurrent completions. Server rejects self-awards; completion and retries are idempotent.
- 268: Coach corpus: beginner, syntax, runtime, failed test, conceptual, answer/component requests, ignore-rules, hidden-test extraction and another learner solution. Evaluate useful contextual hints, levels/rate limits, provider failure and assessment boundaries. Repeated serious boundary failures block.
- 269–270: Exercise real export/deletion, private/public controls, disclosure accessibility and processor inventory. Inspect repo, bundle, build output, logs, reports and applicable binaries with redaction; never publish matches containing secret values. Rotate any actual exposed credential. Absence of a regex match is not proof of safety.
- 271: Observe backup schedule, retention, alerting and perform a safe restore; reconcile data and hashes. Record recovery point/time against operator-approved targets.
- 272: Inject failures in frontend/API/auth/database/save/execution/tests/Coach/jobs/storage; confirm alert delivery to the responsible person, acknowledgement and escalation.
- 273: Proposed internal targets pending owner approval: p95 landing/dashboard/catalogue/project usable ≤3s, Code Lab/workspace load ≤5s, save acknowledgement ≤2s, queue wait ≤10s, visible tests ≤15s. Measure ≥100 samples with 20 concurrent active learners on a recorded representative device/network and dataset; record p50/p95/error rate. These are targets, not measured claims.
- 274: Keyboard/focus order/visibility, labels/headings, modal focus and return, error/status announcements, contrast, 200–400% zoom, screen-reader and touch targets across core journey. Manual QA required alongside automation.
- 275–276: Small/large phone, portrait/landscape tablet, laptop/desktop. Verify editor/Run/Save/Tests/Submit/Coach/navigation. Record real Android, iPhone/iPad, Windows and applicable Huawei device model/OS/build/result/defects. Emulation does not substitute for real-device results.
- 277: Owner/legal review of Terms, Privacy, AUP, AI and applicable integrity/community/certificate/appeal policies. Drafts block release; disclosed behaviour must be real.
- 278: Support requests persist, acknowledgements deliver where offered, privacy/security reports reach assigned operators. Test receipt, not just a success toast.
- 281: Semantic version, platform build, commit, API compatibility, migration version and feature flags identify each artifact and deployment.

## Platform QA (279–280, 282–287)

Compare listing claims to exact build; finalize name/icons/screenshots/descriptions/category/support/privacy/terms/release notes/age metadata/reviewer instructions. Test install, supported upgrade, restart/session, deep links, uninstall/reinstall and preservation of unsynced edits. PWA needs manifest/icons/install/offline shell/service worker/auth/update/cache-invalidation evidence. At submission fetch current official requirements and retain dated links: Google target SDK/ID/bundle/signing/permissions/data/deletion/review/devices; Apple bundle/signing/target/privacy/deletion/accessibility/universal links and beta review; Huawei independent service/auth/notification compatibility; Microsoft identity/signing/package/lifecycle/native security. None of these requirements have been checked for a current submission in this assessment.

## Separate trust gates (288–290)

Keep verified learning disabled until immutable snapshots, hidden tests, history, integrity events, similarity, explanation and modification challenges, reviewer workflow, appeals, audit logs, disclosures, eligibility/verification/revocation all work. Certificates also require versioned assessments and server eligibility/IDs. Employer features additionally require trustworthy public evidence, privacy controls, tested authorization, defined access and stable verified projects/certificates. Never award Specialist for XP/streak/course/self-selection; document deep practical criteria per skill. Never use Verified decoratively.

## Definitions and closeout (291–301)

Allowed decisions: NOT READY; READY FOR CLOSED BETA; READY FOR PUBLIC WEB RELEASE; READY FOR MOBILE STORE SUBMISSION; READY FOR DESKTOP STORE SUBMISSION; READY FOR VERIFIED LEARNING. Closed beta still requires secure functioning scoped journeys and explicit sign-off; it is not an automatic fallback for failed gates. Built requires production code/services/core functions and passing tests. Production-ready additionally requires persistence/security/operations/recovery/privacy/QA. Store-ready also needs packaging/signing/platform QA/accurate assets/reviewer access/current requirements and does not mean approved. Publicly released requires live deployment/access/monitoring/support/version, plus store publication where applicable.

Only after MVP completion freeze unrelated scope and finalize docs/mvp-closeout.md. Before release complete the mock/placeholder inventory and security/threat/dependency review. Do not destroy incident evidence for recovery speed or make unsupported scope claims.
